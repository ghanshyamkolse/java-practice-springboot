The client asks.

You submit a form. The UI sends JSON to its own origin at /api/….

02UI · :3000

Nginx forwards.

The separate UI container serves the page and proxies API requests to the gateway. The browser needs no cross-origin configuration.

03GATEWAY · :8080

A route is chosen.

Spring Cloud Gateway matches the path and resolves the destination service name.

04EUREKA · :8761

An address is found.

Eureka keeps the registry. The gateway uses service discovery and load balancing instead of hard-coded container addresses.

05READING → METER

Services cooperate.

For a new reading, the reading service calls the meter service over HTTP. An unknown meter produces a clear error.

06TWO PRIVATE DATABASES

Owners save their data.

The meter service writes meters; the reading service writes readings. No service reads another service’s database.

03 / ARCHITECTURE NOTES

Small system.
Real trade-offs.

This is a learning environment, not a production-ready platform. Use it to observe how independent services behave.

01Why separate services?+

The meter and reading applications can build and deploy separately. Each owns its business rules and data. The trade-off is that an in-process call becomes a network call that can fail.

02Why a gateway and Eureka?+

The gateway gives the client one entry point. Eureka registers services by name, so routes and clients do not need fixed container IP addresses. The registry helps locate services but cannot guarantee that a request succeeds.

03Why do readings store a meter ID?+

A reading belongs to the reading service, so it stores the meter identifier without a foreign key into the meter database. The reading service checks the meter through its API instead of reaching into its tables.

04What disappears on restart?+

The databases currently use in-memory H2. Restarting a service clears its data. A later exercise replaces H2 with durable databases that remain private to each service.
